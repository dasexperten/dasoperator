## GOAL

Экран `erp.dasexperten.com` → CRM → Orders читает заказы русской витрины **из
нашей собственной D1**, а не из живого HTTP-вызова к `dasexperten.ru` на каждой
загрузке. Витрина остаётся источником истины, но общается с ней ночной
синхронизатор, а не палец Владельца на кнопке.

## WHY — что именно болит

Сегодня каждая холодная загрузка таблицы качает **весь** список из 1846 заказов
одним ответом с шаред-хостинга reg.ru, чтобы показать 50 строк. 28 августа этот
ответ оборвался на 218011 байте с кодом 200 в заголовке, и парсер выплюнул
`Unterminated string in JSON at position 218011` прямо в таблицу Владельцу.

Слой 1 накрыл симптом сохранённой копией, слой 2 снял 429 с сортировки. Причина
цела: **экран зависит от того, здорова ли витрина ровно в ту секунду, когда его
открыли**, и объём растёт линейно с числом заказов. На 5000 заказов это ляжет
насовсем, и никакой кэш этого не отменит.

## ACCEPTANCE — как понять, что готово

1. `GET /api/crm/orders` **не делает ни одного исходящего HTTP-вызова** ни к
   `dasexperten.ru`, ни к `api.kit.yandex.net`. Только D1.
2. Холодный ответ страницы 1 — **быстрее 300 мс** (сегодня 1.5–2.8 с).
3. Сортировка по любой колонке работает по **всем** 1846 строкам, не по
   странице, и не зависит ни от какого внешнего API.
4. Поиск ищет по всей таблице, а не по «последним 800 заказам» сканом.
5. Если витрина лежит сутки — экран показывает данные и плашку
   **данные на <дата>**, а не ошибку.
6. `total_count` на экране совпадает с `total_count` витрины после синка.
7. Ни одна из ошибок в `api/src/routes/crm.ts` не печатает `e.message`
   пользователю — техническая причина только в `details`.

## СХЕМА — предлагается, уточнить по реальному телу фида

```sql
CREATE TABLE IF NOT EXISTS crm_orders_ru (
  order_number   TEXT PRIMARY KEY,
  total_rub      INTEGER NOT NULL DEFAULT 0,
  status         TEXT    NOT NULL,
  created_at     TEXT    NOT NULL,   -- ISO8601 как отдаёт витрина
  customer_key   TEXT,               -- необратимый SHA-256, НЕ телефон
  bonus_charged  INTEGER NOT NULL DEFAULT 0,
  raw_json       TEXT,               -- тело позиции как пришло
  synced_at      INTEGER NOT NULL    -- unix, когда строка обновлена
);
CREATE INDEX IF NOT EXISTS idx_crm_orders_ru_created ON crm_orders_ru(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_crm_orders_ru_status  ON crm_orders_ru(status);
CREATE INDEX IF NOT EXISTS idx_crm_orders_ru_total   ON crm_orders_ru(total_rub);

CREATE TABLE IF NOT EXISTS crm_sync_state (
  feed          TEXT PRIMARY KEY,    -- 'orders_ru'
  last_ok_at    INTEGER,             -- unix последнего удачного синка
  last_try_at   INTEGER,
  rows_upserted INTEGER,
  last_error    TEXT
);
```

## СИНХРОНИЗАТОР — правила

- Крон **каждый час**, свободный слот; ночного одного мало — заказы падают днём.
- Забор через существующий `fetchStorefrontOrders`, тело **валидируем до
  записи**: `total_count` из ответа обязан совпасть с длиной массива. Не совпал
  — **синк отменяется целиком**, `last_error` пишется, старые строки не трогаем.
  Обрыв фида не должен наполовину затереть зеркало.
- Запись **батчами по 100** через `env.DB.batch()`, upsert по `order_number`
  (`ON CONFLICT DO UPDATE`). Полного `DELETE` таблицы не делаем никогда.
- Заказы, исчезнувшие из фида, **не удаляем** — витрина отдаёт хвост не всегда
  целиком, а удалённая строка тихо ломает `total_count` на экране.
- Персональных данных в зеркале нет: имя, телефон, почта в D1 **не пишутся**
  ни при каких условиях. Только `customer_key`. Это ст. 12 152-ФЗ, тот же режим,
  что и сейчас на витрине.

## ЧТЕНИЕ — правила

- `/orders` собирает один `SELECT ... ORDER BY <колонка> LIMIT ? OFFSET ?`.
  Белый список колонок сортировки в коде, никакой склейки имени колонки из
  query-строки.
- Поиск: `WHERE order_number LIKE ?` — по всей таблице.
- Обогащение лояльностью из `loyalty_accounts` / `loyalty_transactions`
  оставляем как есть, чанк по 90 переменных в `IN()` (лимит D1 — 100).
- `data_as_of` в ответе = `crm_sync_state.last_ok_at`, не `Date.now()`.
- Плашка **stale** зажигается, если `last_ok_at` старше 3 часов.

## ROLLBACK

Фид-путь не удалять физически в этом заходе: оставить за флагом
`CRM_ORDERS_SOURCE = "d1" | "feed"` в `[vars]`. Если зеркало соврёт по цифрам —
одна правка `wrangler.toml` и пуш возвращают старое поведение. Флаг снимаем
отдельным коммитом через неделю ровной работы.

## РАБОЧИЙ ЗАКОН

- `origin/main` → правка → commit + push → деплой **только** через GitHub
  Actions. `wrangler deploy` с локальной машины запрещён (RAIL 5).
- Миграция применяется workflow `apply-migration.yml`, руками в D1 не лезем.
- Массив `crons` в `wrangler.toml` Cloudflare **заменяет целиком** на каждом
  деплое — слот добавляем в массив, а не в дашборде.
- После пуша проверить удалённый HEAD через GitHub Contents API с
  cache-bust, локальный `git rev-parse` ничего не доказывает (§8.1).
- Изменили закон — меняем его во всех местах, где он записан, в той же сессии.

## ВОПРОСЫ К ВЛАДЕЛЬЦУ — до начала работ

1. **Час или ночь?** Часовой синк даёт свежесть в пределах 60 минут. Ночной
   дешевле, но заказ, оформленный утром, появится в ERP на следующие сутки.
2. **Держим ли историю удалённых заказов?** Предлагается держать: зеркало
   растёт, но цифры не прыгают.
3. **Возвращаем ли имена и телефоны по кнопке?** Сегодня их нет вовсе. Если да —
   это отдельная работа с уведомлением по ст. 12 и журналом доступа, и в этот
   goal она не входит.
